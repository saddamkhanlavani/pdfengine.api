Running headers and footers

T1-1 · string-set + @page margin boxes
The issue Every real report needs the current chapter in its header. Chromium's PDF export takes headerTemplate — one fixed template for the entire document. It cannot change per page, so "the current chapter" is impossible through it. Chromium also discards string-set before the stylesheet is ever exposed to script, so the value cannot even be read.
The fix The engine reads string-set from the raw stylesheet, records every assignment, then resolves which page each one landed on by searching the finished PDF — not by estimating from the DOM, which was measured wrong twice. The header is then drawn per page, the same mechanism that stamps watermarks.
See it here Top-left of this page reads Running headers and footers. Turn the page and it changes by itself. Bottom-right counts real pages, and the total is the real total.

The value carries forward correctly too: a section long enough to span several pages keeps its title in the header on the pages that contain no heading at all.

Cross-references and leaders

T1-2 · target-counter()    T1-3 · leader()
The issue A page number does not exist until the document has been paginated. Two earlier attempts computed them from DOM geometry and both produced wrong numbers: counting forced breaks missed pages created by ordinary overflow, and dividing by scroll height mis-attributed pages because forced breaks make DOM coordinates non-linear. Separately, the engine only understood its own proprietary attribute, so migrating a Prince or DocRaptor template meant rewriting it.
The fix Render once, locate each target's text in the real pages, substitute the true numbers, render again — the same multi-pass approach Prince itself uses. Standard target-counter(attr(href), page) is translated onto that resolver, so existing templates work unmodified. leader('.') fills the space between the title and the number.
See it here Go back to Contents. The dots are the leaders. The numbers are real — check any one of them against the page it points to.

A reference that cannot be resolved renders as ? plus a diagnostic, never as a silent blank — a reader cannot tell an empty gap from a design choice.

Cover pages and mirrored margins

T1-4 · @page :first / :left / :right
The issue These looked broken and were logged as missing engine work. Measuring showed Chromium already implements all three. They were dead for a different reason: the HTML sanitizer necessarily drops CSS it does not recognise, and it was stripping every @page descriptor on the way through — including size, which is why every document silently came out A4 regardless of what it asked for.
The fix Stop stripping @page, and parse paged-media CSS from the pre-sanitizer source. This one needed a gate, not an implementation — and it is the reason the sanitizer is now the first suspect whenever a paged-media feature does nothing.
See it here Page 1. Its margins are visibly wider than every other page in this document. That is @page :first { margin: 52mm 30mm } doing exactly what it says.

Footnotes

T1-5 · float: footnote
The issue Legal, academic and financial documents need footnotes. Chromium supports none of the mechanism: content marked float: footnote renders inline, exactly where it was writtenMeasured 2026-08-18: the test marker landed 16% of the way down page 1 instead of at the page bottom., and neither ::footnote-call nor ::footnote-marker numbers anything.
The fix The engine lifts each footnote out of the flow and leaves a numbered call marker behind. It then resolves which page that call landed on from the finished PDF, reserves space at the bottom of the page, and re-renders — because adding footnote area changes pagination and can move a call to a different pageThe loop iterates until every page holding a call has room, and reports rather than overlapping text if it cannot settle..
See it here Two superscript markers above, and the matching notes at the foot of this page, below the rule — not where they were written in the source.

Both notes were authored in the middle of the paragraphs above. Neither appears there.

Widow and orphan control

T1-6 · orphans / widows
The issue Logged as needing a line-breaking engine. Measuring showed Chromium implements orphans and widows correctly — at a setting of 4, a paragraph that would have split 5/3 moved whole to the next page. The real gaps were smaller and more specific: the values were hard-coded to 2 with no way for a caller to change them, and the one case CSS cannot satisfy — a block taller than a page — degraded in silence.
The fix Expose orphans and widows as options rather than re-implementing line breaking, and measure real line boxes so a block that can never satisfy the request is reported instead of quietly split.
See it here Nowhere in this document is a single line of a paragraph stranded by itself at a page boundary. That is the feature working; its success looks like nothing being wrong.

Named pages

T1-7 · @page wide + page: wide
The issue A landscape fold-out inside a portrait report, or a cover with its own paper. CSS expresses it as @page wide { size: A4 landscape } plus page: wide. Chromium silently ignores it — measured, a section declared A4 landscape with 50mm margins came out with byte-identical geometry to the body pages. It cannot be corrected after rendering, because page size changes layout, not just what is stamped on top.
The fix Consecutive content sharing a page name forms a run. Each run is rendered on its own paper and the parts are stitched into one document. Everything document-wide is then resolved against the stitched result — page counters, cross-references, footnote placement and the bookmark outline — because a run only knows about itself.
See it here This page is landscape. The pages before and after it are portrait, in the same file, with the same header and a continuous page count.

Page floats

T1-8 · float: top / float: bottom
Figure 1 — This block was written in the middle of the text below. It is printed at the foot of the page because it asks for float: bottom.
The issue A figure that lands halfway through a paragraph interrupts the reading. Print typesetting pins it to the top or bottom of the page instead. Chromium implements neither edge — measured, a float: top box and a float: bottom box landed at the identical position, indistinguishable from no float at all.
The fix The same machinery as footnotes: lift it out of the flow, resolve its page from the finished PDF, reserve the band, re-render, draw. One honest difference — a float is arbitrary content, so it cannot be rebuilt from a text description. It is captured as an image at twice its size while the browser still has it laid out.
See it here Figure 1, at the foot of this page, below this text. In the source it sits above this paragraph.

Per-page reservation

T1-9 · footnoteReservationMode
The issue Reserving footnote space by growing the page margin is correct but blunt: it is uniform, so a document with one crowded page loses that band on every page, including the ones carrying no footnotes at all. Reserving per page instead costs one extra render per page — a page break moves every later page, so no two pages can be measured from the same render.
The fix Neither strategy is right for every document, and the caller cannot tell which they need by looking at their HTML — it depends on how unevenly the footnotes fall, which only exists once the document has been paginated. So the engine measures both costs after the first render and chooses. Measured: a document with five footnotes crowded onto one page reclaimed 76 points of height on a footnote-free page.
See it here The render diagnostics for this document contain a line beginning Footnote reservation: naming the strategy chosen, what the alternative would have cost in points, and how many extra renders it was worth. Set footnoteReservationMode to "uniform" or "per-page" to overrule it.

Why it is decided rather than configured: a switch left to the caller is a switch set wrong. Off by default and some documents silently lose a page of content; on by default and every document pays for renders it does not need.

Attachments and e-invoicing

T2-1 · embedded files
The issue An EU e-invoice is one PDF that a human reads and a machine reads: the page for the person, an embedded XML file for the buyer's accounting system. Without embedded files the engine cannot produce Factur-X or ZUGFeRD at all — not badly, at all — and an entire revenue vertical is closed.
The fix Each file is written as an /EmbeddedFile stream plus a /Filespec, registered BOTH in the catalog's name tree (what the attachment pane lists) and in /AF (what makes it an associated file, which PDF/A-3 requires). The backlog assumed a library change was needed; measuring showed the current library already exposed everything required.
See it here Open this document's attachment pane. factur-x.xml is in it, and it extracts byte-identical to what was supplied. A PDF/A-2b request with an attachment is REFUSED with a 400, because PDF/A-2 permits only embedded PDF/A documents — producing it anyway would hand you an invoice your recipient rejects.

One bug worth keeping. A MIME type contains a /, which a PDF name cannot. Hand-escaping it to text#2Fxml got escaped again on save to text#232Fxml, and veraPDF failed PDF/A-3 clause 6.8. For an e-invoice that is a rejected invoice, not a cosmetic defect.

Digital signatures

T2-2 · PAdES B-T and B-LT
The issue A signature that merely exists is worthless. Three things have to be true: it must verify in tooling nobody here wrote; tampering must break it; and it must still verify after the signing certificate expires — which a bare signature does not, because the only evidence of when it was signed is a clock the signer controls.
The fix A detached CMS signature over exactly the byte ranges the finished file declares, with the attributes CAdES requires. timestampUrl attaches an RFC 3161 timestamp from a trusted authority (PAdES B-T). embedValidationData appends the certificate chain and its revocation lists as an incremental update, so the document carries its own evidence and validates with no network at all (PAdES B-LT).
See it here Open the signature panel. This document is signed, timestamped and carries embedded validation data. Change one byte of it and the signature fails.

What measurement forced. The PDF library's own signing could not be used: it hands the signer 2,133 bytes beginning with whitespace while writing a byte range declaring 2,922 beginning at the file header. openssl rejects the result. The signature is therefore computed here, over exactly what the finished file declares.

Not claimed: the signature is invisible (it seals the document and draws nothing), and signing cannot be combined with encryption or fast web view — both rewrite the bytes a signature seals, so both are refused rather than silently producing a signature that does not verify.

Fillable form fields

T2-3 · AcroForm
The issue Applications, consent forms and tax returns need fields a person can type into. This was recorded as BLOCKED on the PDF library for good reason: the field classes in both candidate libraries have zero public constructors, so there is no API to call.
The fix The observation was true and the conclusion was wrong. A form field is not a library type — it is a widget annotation on a page plus an entry in the catalog's /AcroForm, and both are ordinary dictionaries this engine already writes by hand for attachments. What was missing was a convenience API, not the capability.

Page operations and fast web view

T2-4 · extract / rotate / flatten / N-up    T2-5 · linearization
The issue Document assembly needs the mechanical operations: pull pages out, turn them, put several on a sheet, remove interactivity. Separately, a large PDF opened over HTTP makes the reader wait for the whole file before it can paint page one.
The fix One transform endpoint for the page operations. extract preserves the order written, so 3,1 reorders and 1,1 duplicates — sorting the selection would quietly refuse what was asked. rotate is additive, so a page already turned is turned BY the amount asked rather than reset TO it. nup keeps text as text. flatten removes interactivity without rasterising, so the document stays searchable.
See it here Not visible on a page — these operate on a finished PDF. Post this document to /api/v1/pdf/transform with operation: "nup" and you get these pages two to a sheet, still selectable. Linearization is verified by asking qpdf, the reference implementation, whether the result is linearized.

Refused rather than silently dropped: fast web view plus signing. Applying the signature rewrites the document and undoes the page ordering, so you would get a file that is signed and not linearized, with nothing to tell you.

Print production

T2-6 · bleed, crop marks, page boxes
The issue A commercial printer trims a sheet with a blade that lands a fraction out. If artwork stops exactly at the finished edge, the trim leaves a white sliver. The artwork has to run PAST the cut line, and the file has to record where that line is.
The fix Bleed is applied at RENDER time — the page is rendered larger so backgrounds genuinely extend past the cut — and the finished size is recorded as the TrimBox, taken from the nominal paper rather than the rendered box so it is exact to a hundredth of a millimetre. Crop marks key off that rectangle and sit outside the bleed, so none prints inside the finished page.
See it here Not on this page, deliberately — a proof sheet you read on screen should not be trimmed. Render any template with bleedMm: 3 and inspect its page boxes.

The bug this had, and how it was found. It was asked whether the feature was real or present. Landscape was ignored: an A4 landscape job produced a PORTRAIT trim box, so every landscape print would have been cut wrong. It had only ever been tried on A4 portrait.

Not claimed: CMYK and PDF/X. Converting to CMYK needs a colour-management pipeline, and the usual engine for it is AGPL-licensed — a licensing decision, not an engineering one. No validator available here checks PDF/X, so conformance could not be proven even if attempted. Every print job says so at render time.

What this engine does not do yet

Kept deliberately short and specific. Every limitation this page listed in earlier revisions has now been closed. What follows is the record of what each one was and how it was answered — and one item that was never a gap, only a decision the engine now makes for you.

ItemWhere it standsWarned at render?
Links inside footnotes Closed. A citation link in a footnote is drawn in link colour and carries a real PDF annotation, so it is clickable. The footnote's text arrives complete, with punctuation attached exactly as authored. n/a — it works
Floated figures had no text layer Closed. The picture is still what you see, but every word inside it is re-drawn over the image as invisible text at the same coordinates — the technique a scanned document uses for its OCR layer. A floated table is now selectable, searchable and readable by a screen reader. n/a — it works
Bold and italic inside footnotes Closed. Emphasis is drawn in a real bold or italic face. It needed two things: font files carrying those faces, and a font resolver — PdfSharpCore had none registered, so every family and every style resolved to one identical face, which also meant a font-family asked for in a margin box had never had any effect. Carlito, Caladea and Liberation Mono are bundled for it, all under the SIL Open Font License. Faking it by double-striking was built first and rejected: it thickens the stem but puts the word in the text layer twice, so the footnote copied out as 'Smith Smith v.v. Jones'. Only if a Regular-only family is requested
Footnote space reservation Not a gap — the engine decides. Reserving uniformly is one cheap re-render but costs every page the tallest band; reserving per page reclaims that at one render per page. Which is right depends on how unevenly the footnotes fall, which is only knowable after a render — so the engine measures it and picks, then says which it chose and what it was worth. Yes — states the decision

Why any of this is printed here. The rule this engine follows is that degradation is REPORTED, never discovered. Anything above that affects your document appears as a warning on the render that produced it, naming how many elements were affected — so you learn it from the response, not from a customer.
